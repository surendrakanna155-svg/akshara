## Architecture Strengths

1. **Consistent ERP pattern** — Screen → Riverpod Provider → Repository Interface → Mock/API implementation across all 11 admin modules.
2. **Centralized routing** — `RouteNames` + `app_router.dart` + per-module `*_navigation.dart` route builders.
3. **AdminShell** — Unified desktop/tablet/mobile drawer for all ERP modules with persona-filtered nav rail.
4. **Shared design system** — `AksharaKpiCard`, `AksharaStatusChip`, loading/empty/error states used consistently in ERP modules.
5. **API swap readiness** — `useApiRepositoriesProvider` + `Api*Repository` scaffolding for all 11 repos without UI changes.
6. **Test discipline** — Per-module provider + screen tests, router smoke tests, repository tests, golden tests, CI pipeline.
7. **Release documentation trail** — 14 versioned release docs with consistent structure.

---

## Architecture Weaknesses

1. **Triplicated ERP scaffolding** — 11 near-identical `*ModuleScaffold`, `*SubNav`, `*KpiRow`, `*TrendChart`, `*SegmentPanel` sets (~55 wrapper files).
2. **Dual data architectures** — ERP uses repositories; mobile apps (Parent/Teacher/Student) still embed mock data in feature providers.
3. **Synchronous repository contracts** — All interfaces use sync getters; API integration will require async migration or blocking calls.
4. **No real authentication** — Demo OTP + `UserRole` enum; `adminPersonaProvider` always returns `superAdmin` for staff.
5. **No server-side RBAC** — Route guards are client-only, role-coarse (4 roles, not 16 personas).
6. **Stale reference docs** — `RouteInventory.md` and `SharedWidgetInventory.md` last updated v0.5.1; do not reflect v1.4 scope.
7. **Large monolithic router** — `app_router.dart` ~1,450 lines; all shells and modules in one file.
8. **No offline/sync layer** — TechnicalArchitecture specifies Drift/Hive; not implemented.
