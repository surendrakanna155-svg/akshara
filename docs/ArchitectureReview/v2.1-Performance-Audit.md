# v2.1 — Performance Audit

**Date:** June 2026  
**Scope:** Provider architecture, rebuild risks, list rendering, pagination, large dataset readiness  
**Inputs:** v1.7 Performance section, v2.1 system inventory  
**Constraint:** Read-only — no code modified

**Performance readiness: 6.5 / 10** (adequate for mock/demo scale; risks at production data volume)

---

## 1. Executive Summary

Akshara ERP performs well at **demo/mock data scale** (~5–50 rows per table). Production risks emerge from **868 Riverpod providers**, **non-virtualized DataTables**, **absence of server pagination**, and **broad tenant-change invalidation**. No performance regressions detected in test suite; no load/perf tests exist.

---

## 2. Provider Count & Rebuild Risk — **6 / 10**

| Metric | Count | Risk |
|--------|------:|------|
| Total provider declarations | **868** | High graph complexity |
| Loading/Error/Empty triads | ~270 state providers | Redundant watches |
| ViewState providers (Adm + Fin) | ~22 | Additional layer |
| `ref.watch(repositoryQueryProvider)` fan-out | All ERP FutureProviders | Full module reload on tenant switch |

### Rebuild hotspots

| Pattern | Location | Risk |
|---------|----------|------|
| `watchRepositoryFuture` + manual overrides | All ERP providers | Triple watch per screen |
| Filtered derived providers | Leads, collections, defaulters, refunds | Recomputes on any parent change |
| Large monolithic provider files | `control_center_providers.dart` (57), `hr_providers.dart` (55) | Hard to optimize selectively |
| Admin nav rebuild | `admin_navigation_provider.dart` | Rebuilds on any permission change |

### Mitigations already present

- `FutureProvider` caching — avoids redundant network until invalidated
- Feature-flag repo swap is compile-time stable
- Riverpod auto-dispose on most FutureProviders (default)

### Recommendations

| Priority | Action |
|----------|--------|
| P1 | Consolidate Loading/Error/Empty into ViewState only (halve provider count) |
| P2 | `select()` for narrow watches on large provider graphs |
| P2 | Split mega-provider files by screen domain |

## 3. List Virtualization — **4 / 10**

| Pattern | Usage | Virtualized |
|---------|------:|:-----------:|
| `DataTable` inside `SingleChildScrollView` | ~40 ERP tables | ❌ |
| `Column` with `for` loops (mobile cards) | ~30 screens | ❌ |
| `ListView.builder` | 2 files (parent receipts, teacher conversation) | ✅ |
| `SliverList` | 1 file (admin nav rail) | ✅ |

**Finding:** ERP admin modules render **full lists in memory**. Acceptable for 5–20 mock rows; will jank at 500+ rows.

### High-risk screens (large production datasets)

| Screen | Widget pattern | Expected prod rows |
|--------|---------------|-------------------:|
| Admissions leads | DataTable | 1,000+ |
| SIS registry | DataTable | 5,000+ |
| Finance collections | DataTable | 10,000+ |
| HR employees | DataTable | 200+ |
| Transport allocation | DataTable | 500+ |

---

## 4. Pagination Readiness — **3 / 10**

| Layer | Pagination support |
|-------|-------------------|
| `PaginationDto` (API) | ✅ Parsed in admissions DTOs |
| Repository interfaces | ❌ No cursor/page params |
| `RepositoryQuery` | ❌ No pagination fields |
| Remote datasources | ❌ No page/limit query params |
| UI (load more / infinite scroll) | ❌ Not implemented |
| Mappers | ❌ Pagination discarded |

**Verdict:** Infrastructure exists at DTO layer only. **Not production-ready for large lists.**

## 5. Large Dataset Risks

| ID | Risk | Trigger | Impact |
|----|------|---------|--------|
| PERF-01 | Full list fetch + render | API returns 1000+ leads | UI freeze, OOM on mobile |
| PERF-02 | No debounce on search filters | Student account search | Rebuild storm |
| PERF-03 | Multiple FutureProviders per screen | Collections (list + daily summary) | 2× network on mount |
| PERF-04 | Chart widgets with unbounded points | Finance/Admissions trends | Canvas overdraw |
| PERF-05 | Tenant switch invalidates all futures | Multi-school admin | Full ERP reload |
| PERF-06 | 868-provider graph startup | Cold start | Slower first frame |
| PERF-07 | Golden tests only on 3 mobile dashboards | — | No ERP perf baseline |

## 6. Network & Caching — **7 / 10**

| Capability | Status |
|------------|--------|
| Dio singleton | ✅ |
| Request correlation ID | ✅ |
| Proactive JWT refresh | ✅ |
| Response caching | ❌ |
| Stale-while-revalidate | ❌ |
| Retry with backoff (non-auth) | ❌ |
| Circuit breaker | ❌ |

API modules re-fetch on every `ref.invalidate()` — no local cache layer.

## 7. Mobile Performance — **7 / 10**

| Factor | Assessment |
|--------|------------|
| Screen count | 28 ( manageable) |
| Mock providers (sync) | Fast — no async overhead |
| Scroll views | Mostly `SingleChildScrollView` — OK for small data |
| Golden tests | 3 dashboards — visual regression only |
| Image/asset load | Minimal |

Mobile apps perform well today because data is **small and synchronous**. Will degrade when wired to API without pagination.
