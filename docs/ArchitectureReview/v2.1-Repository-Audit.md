# v2.1 — Repository Architecture Audit

**Date:** June 2026  
**Scope:** All 11 ERP repository domains, 102 async methods  
**Inputs:** v1.5 Repository Audit, v1.6–v1.9 API work, v2.1 Finance API  
**Constraint:** Read-only — no code modified

**Repository readiness score: 8.5 / 10** (ERP mock-MVP + 2 live modules)

---

## 1. Executive Summary

The repository layer is the **strongest architectural pillar** in Akshara ERP. All 102 methods are async, tenant-scoped via `RepositoryQuery`, and swappable between mock and API implementations via per-module feature flags. Two modules (Admissions, Finance) are fully live; nine remain scaffold-only.

## 3. Async Patterns — **8.5 / 10**

### Provider stack (ERP modules)

```
repositoryQueryProvider (tenant)
  → *FutureProvider (calls repository)
    → *Provider (watchRepositoryFuture + manual overrides)
      → *ViewStateProvider (Admissions/Finance only)
        → Screen (*AsyncBody or legacy loading/error)
```

### Strengths

- `watchRepositoryFuture` centralizes loading/error/empty for widget tests
- `FutureProvider` enables automatic async lifecycle
- Feature-flag swap is transparent to UI when mock data shapes match API mappers

### Risks

| ID | Risk | Impact |
|----|------|--------|
| REP-A01 | Dual async state (legacy triads + ViewState) in API modules | Provider bloat (~868 total declarations) |
| REP-A02 | 9 modules still use legacy-only pattern (no ApiFailure retry) | Will need migration when API enabled |
| REP-A03 | `ref.watch(repositoryQueryProvider)` in every FutureProvider | Tenant change invalidates all futures (correct but broad rebuild) |
| REP-A04 | No `AsyncNotifier` / mutation pattern for write operations | Future POST/PUT will need new abstraction |

## 4. RepositoryQuery Usage — **8 / 10**

**File:** `lib/core/repositories/repository_query.dart`

```dart
class RepositoryQuery {
  const RepositoryQuery({
    required this.tenantId,
    this.schoolId,
    this.organizationId,
  });
}
```

| Usage | Status |
|-------|--------|
| Passed to all 102 repository methods | ✅ |
| Sourced from `repositoryQueryProvider` | ✅ |
| Derived from `tenantContextProvider` + auth claims | ✅ |
| Serialized as query params in remote datasources | ✅ |
| Duplicated in HTTP headers via `TenantInterceptor` | ⚠️ Dual propagation |

### Gaps

- No `userId`, pagination cursor, sort, or filter fields
- No immutability helpers for query copy-with
- Demo tenant fallback when unauthenticated (`TenantContext.demo`)

## 5. Tenant Propagation — **7.5 / 10**

### Flow

```
Auth claims → tenantContextProvider → repositoryQueryProvider
  → Repository method → Remote _queryParams()
  → TenantInterceptor → X-Tenant-Id, X-School-Id, X-Organization-Id, X-User-Id headers
```

### Strengths

- End-to-end tenant context from auth to HTTP
- `TenantInterceptor` rejects requests when tenant required but missing
- Consistent demo query for tests: `RepositoryQuery.demo`

### Risks

| ID | Risk | Severity |
|----|------|----------|
| REP-T01 | Unauthenticated API calls send demo tenant headers | P1 |
| REP-T02 | Client-supplied tenant from JWT — not server-validated binding | P0 (production) |
| REP-T03 | Headers + query params duplicate tenant — drift risk | P2 |
| REP-T04 | No cross-tenant isolation tests | P1 |
