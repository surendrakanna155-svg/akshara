# v6.1 Phase 4B3B — Finance Invoices Client Alignment

**Document ID:** `AKS-PHASE4B3B-FINANCE-CLIENT-INVOICES-v1.0`  
**Status:** Architecture only — no Flutter code, no backend code, no deployment  
**Baseline:** Phase 4B3A backend (`finance_invoices`, auto-invoice on assignment, 4 REST routes)  
**Upstream:** `v6.1-Finance-Invoices-Mapping.md`, `v6.1-Finance-Implementation-Mapping.md`, deployed 4B2 contracts

---

## 1. Purpose

Close the **DRIFT FLAG** identified in the 4B3A contract audit: the Flutter client has zero invoice repository surface while the backend exposes list/get/issue/cancel APIs. This document defines the smallest compatible client contract and a phased migration strategy without implementing code.

### Scope

| In scope | Out of scope |
|----------|--------------|
| `FinanceInvoice` DTO | Collections, receipts, refunds |
| `FinanceRepository` invoice methods | Parent/student portal invoice APIs |
| `FinanceApiPaths` additions | Dashboard/analytics widgets |
| Mapping to `InstallmentHistoryEntry` | Multi-term invoice split (4B3c+) |
| Mock + API repository wiring plan | Platform `BillingInvoice` (Control Center) |

## 3. Proposed `FinanceInvoice` DTO

Add to `lib/features/finance/finance_models.dart`:

```dart
enum InvoiceStatus {
  draft,
  issued,
  partiallyPaid,
  paid,
  cancelled,
}

@immutable
class FinanceInvoice {
  const FinanceInvoice({
    required this.id,
    required this.studentId,
    required this.feeAssignmentId,
    required this.academicYear,
    required this.invoiceNumber,
    required this.invoiceDate,
    required this.dueDate,
    required this.subtotalAmount,
    required this.discountAmount,
    required this.totalAmount,
    required this.outstandingAmount,
    required this.paidAmount,
    required this.invoiceStatus,
    required this.termLabel,
    required this.createdBy,
    required this.createdAt,
    required this.updatedAt,
  });

  final String id;
  final String studentId;
  final String feeAssignmentId;
  final String academicYear;
  final String invoiceNumber;
  final String invoiceDate;
  final String dueDate;
  final String subtotalAmount;
  final String discountAmount;
  final String totalAmount;
  final String outstandingAmount;
  final String paidAmount;
  final InvoiceStatus invoiceStatus;
  final String termLabel;
  final String createdBy;
  final String createdAt;
  final String updatedAt;
}
```

### Design notes

- Amounts remain **strings** (matches existing finance models — `StudentFeeAccount.totalDue`, etc.).
- `paidAmount` is **computed server-side** (`totalAmount − outstandingAmount`); client does not derive it.
- `termLabel` is `"Annual"` for 4B3A (N=1); future multi-term invoices populate per-row labels.
- Do **not** conflate with `BillingInvoice` in Control Center — separate domain, separate screens.

## 7. Mapping to `InstallmentHistoryEntry`

Today, `InstallmentHistoryEntry` lives on `CollectionDetail.installmentHistory` and uses **`CollectionStatus`** (`completed`, `pending`, `failed`, `refunded`). Invoices use **`InvoiceStatus`** — a different lifecycle.

### Field mapping (invoice → installment row)

Use when rendering a student's fee timeline from invoices (future Parent P-09 / collection detail enrichment):

| `FinanceInvoice` | `InstallmentHistoryEntry` | Rule |
|------------------|---------------------------|------|
| `id` | `id` | Direct |
| `termLabel` | `termLabel` | Direct (`"Annual"` in 4B3A) |
| `dueDate` | `dueDate` | Direct (ISO date string) |
| `totalAmount` | `amount` | Direct |
| `paidAmount` | `paidAmount` | Direct (from API) |
| `invoiceStatus` | `status` | **See status bridge §7.1** |

### 7.1 Status bridge (`InvoiceStatus` → `CollectionStatus`)

`InstallmentHistoryEntry.status` is `CollectionStatus`, not `InvoiceStatus`. Use a dedicated mapper — do **not** overload `parseCollectionStatus`:

```dart
CollectionStatus installmentStatusFromInvoice(InvoiceStatus invoiceStatus) =>
    switch (invoiceStatus) {
      InvoiceStatus.paid => CollectionStatus.completed,
      InvoiceStatus.partiallyPaid => CollectionStatus.pending,
      InvoiceStatus.issued => CollectionStatus.pending,
      InvoiceStatus.draft => CollectionStatus.pending,
      InvoiceStatus.cancelled => CollectionStatus.failed,
    };
```

Add inverse mapping when sending client state to API (if ever needed):

| `CollectionStatus` | Display only — do not write back to invoice API in 4B3B |

### 7.2 Convenience adapter

```dart
InstallmentHistoryEntry invoiceToInstallmentHistory(FinanceInvoice invoice) =>
    InstallmentHistoryEntry(
      id: invoice.id,
      termLabel: invoice.termLabel,
      dueDate: invoice.dueDate,
      amount: invoice.totalAmount,
      paidAmount: invoice.paidAmount,
      status: installmentStatusFromInvoice(invoice.invoiceStatus),
    );
```

Place in `FinanceMapper` or a small `finance_invoice_adapters.dart` to keep collection vs invoice concerns separated.

### 7.3 Where installment history is sourced (phased)

| Phase | Source | Notes |
|-------|--------|-------|
| **4B3B (this slice)** | `GET /finance/invoices?studentId=` filter TBD | Backend list has no student filter yet; client filters in-memory or backend adds `studentId` query param in 4B3B-backend micro-slice |
| **4B4 collections** | Collection detail API returns `installmentHistory[]` populated from invoices server-side | Preferred long-term — single source of truth |

**Recommendation:** Add optional `studentId` query param to `GET /finance/invoices` in a tiny 4B3B-backend follow-up before building parent timeline screens. Document as dependency; not blocking list/detail/issue/cancel admin screens.

## 8. Flutter migration strategy

### Phase A — Contract scaffolding (no UI)

1. Add `InvoiceStatus`, `FinanceInvoice` to `finance_models.dart`
2. Add four methods to `FinanceRepository` interface
3. Add `FinanceApiPaths` + DTO + mapper methods
4. Implement `ApiFinanceRepository` invoice methods (delegate to remote datasource)
5. Extend `MockFinanceRepository` with 1 invoice per mock assignment (issued, annual)
6. Add enum codec tests + mapper round-trip tests

**Exit criteria:** Repository switch (`RepositoryConfig.useApi`) returns real/mock invoices; no screen changes yet.

### Phase B — Admin finance screens (school staff)

Target screens (existing finance module placeholders / future slices):

| Screen | Repository call |
|--------|-----------------|
| Student account detail (invoice tab) | `getInvoices` filtered by `studentId` |
| Invoice detail drawer | `getInvoice` |
| Issue draft action | `issueInvoice` |
| Cancel invoice action | `cancelInvoice` |

Wire Riverpod providers following `admissions_*_provider.dart` async state pattern.

**Exit criteria:** School admin with `viewFinance`/`manageFinance` can list, view, issue, cancel via API mode on staging.

### Phase C — Installment history enrichment

1. Add `invoiceToInstallmentHistory` adapter
2. When `CollectionDetail.installmentHistory` is empty and account has assignment, fallback-fetch invoices for student
3. Remove fallback once 4B4 collection detail API embeds invoice rows

**Exit criteria:** Collection detail / student fee views show annual invoice row consistent with backend.

### Phase D — Parent portal (deferred)

Parent invoice visibility requires backend RLS policy (`parent_sees_linked_child_invoice`) — explicitly deferred in 4B3A. Do **not** wire parent repository methods until 4B3d backend slice ships.

## 9. Mock data conventions

Mock invoices must honour 4B3A invariants:

| Rule | Mock value |
|------|------------|
| One invoice per assignment | UNIQUE `feeAssignmentId` |
| Auto-gen status | `InvoiceStatus.issued` for assignment-created rows |
| Amounts | `totalAmount == outstandingAmount`, `paidAmount == "0"` initially |
| Term | `termLabel: "Annual"` |
| Due date | ~30 days after `invoiceDate` |

Link mock invoice IDs to existing mock student accounts via shared `feeAssignmentId` constants.

## 10. Error handling alignment

Map backend envelopes to client exceptions (consistent with admissions/finance 4B2):

| HTTP | Code | Client action |
|------|------|---------------|
| 403 | `FORBIDDEN` | Scope/permission — show RBAC denied state |
| 404 | `NOT_FOUND` | Invoice missing or cross-tenant |
| 409 | `CONFLICT` | Reserved for future duplicate create |
| 422 | `VALIDATION_ERROR` | Invalid transition (issue non-draft, cancel paid) |
