# Backup & Restore — Operational Runbook

Operator-facing disaster-recovery procedure for the Akshara VPS pilot. Restore is
**operator-assisted only** — performed over SSH using the scripts in
`deploy/akshara-vps/backup/`. There is **no self-serve restore endpoint** and no
in-app restore button; the Admin → Backup & Restore screen is read-only status
plus school-owned exports.

> Scope: single-VPS pilot. Backups are nightly, encrypted (AES-256), recorded in
> the `ops_backup_runs` ledger, and replicated off the box. Restore drills run
> monthly into a throwaway database.

---

## 1. How backups are produced

| Item | Reality |
|------|---------|
| Script | `deploy/akshara-vps/backup/akshara-backup.sh` (cron, nightly; `manual` arg for ad-hoc) |
| Format | `pg_dump` custom/compressed, streamed straight into AES-256 (plaintext never hits disk) |
| Encryption key | `/opt/akshara/backup/secret.key` (generated by `install-ops-cron.sh`, mode 600) |
| Ledger | each run writes a row to `ops_backup_runs` (size, sha256, location, success/fail) |
| Off-site | encrypted artifact copied off the box via `rclone` (if configured) |
| Retention | grandfather-father-son: monthly (1st) · weekly (Sun) · daily |
| Health probe | operator-only `/health/backup` reads the ledger → 200 fresh / 503 stale-or-missing |

Backup freshness, the latest run result, and the last restore-drill status are all
surfaced on `/health/backup` (internal-health-token gated — operators only).

## 2. Restore procedure (disaster recovery) — operator over SSH

**Pre-conditions**

- You have SSH access to the VPS and `sudo`.
- The encryption key file `/opt/akshara/backup/secret.key` is present.
- You have identified the artifact to restore (newest verified
  `akshara_db_*.dump.enc` in the backup root).
- A maintenance window is agreed and affected schools are notified.

**Step 1 — Verify the artifact restores cleanly into a THROWAWAY db FIRST.**
Never go straight to production. Restore into a scratch db (or run the drill):

```bash
cd /opt/akshara/backup
./akshara-restore.sh akshara_db_YYYYMMDD_HHMMSS.dump.enc akshara_restore_check
```

`akshara-restore.sh` decrypts to `/dev/null` to validate the key/padding, recreates
the target db (when it is NOT the live db), and `pg_restore`s into it
(`--clean --if-exists --no-owner --no-acl`). It **refuses to write over the live db
`$AKSHARA_DB_NAME` without `--force`**.

**Step 2 — Sanity-check the throwaway restore** (the drill automates this; if doing
it by hand, confirm `> 100` public tables and a non-empty `organizations` table —
see §3).

**Step 3 — Production restore (only after the throwaway restore is clean).**
This OVERWRITES the live database and requires the explicit `--force` flag:

```bash
./akshara-restore.sh akshara_db_YYYYMMDD_HHMMSS.dump.enc "$AKSHARA_DB_NAME" --force
```

Without `--force` the script aborts with
`refusing to restore over live DB '...' without --force`. That guard is intentional —
typing `--force` is the operator's deliberate "yes, overwrite production" act.

**Step 4 — Post-restore verification**

- App login works; a known school's SIS counts and a fee balance sample look right.
- Spot-check the audit chain and exam-publish state.
- `/health/backup` and tenant-isolation self-test are green.

## 3. Restore-drill integrity thresholds

`deploy/akshara-vps/backup/akshara-restore-drill.sh` runs monthly (cron, 03:30 on
the 2nd, after the 1st's monthly backup exists). It restores the latest backup into
a throwaway db, integrity-checks it, records the result in `ops_restore_drills`, then
drops the throwaway db. A drill is recorded **`success` only when both** hold:

| Threshold | Source | Failure |
|-----------|--------|---------|
| `> 100` public tables | `information_schema.tables WHERE table_schema='public'` | "restored db has too few tables (N, expected >100)" |
| `organizations` non-empty | `SELECT count(*) FROM organizations` | "organizations table empty after restore" |

Otherwise the drill row is `failed` with the `mismatch` reason and the script exits
non-zero. `/health/backup` surfaces the latest drill's `status` / `tablesChecked` /
`mismatch` verbatim so a failed drill is visible to operators.

> "A backup you have never restored is not a backup." The monthly drill is the proof
> the nightly backups are actually restorable.

---

## 4. School-owned exports

Schools can self-serve **exports** (Admin → Backup & Restore → Export package) to
Download / Google Drive / OneDrive. Exports are a school-owned data copy, not a DR
restore path, and are independent of the operator restore procedure above.

---

## 5. Current RPO / RTO

- This nightly system gives **RPO ≈ 24h** (worst case, one day's data) with a manual
  operator restore for RTO.
- A tighter RPO (the 15-minute target in
  `docs/DEPLOYMENT_MODEL_AND_DR_PLAN.md`) needs **WAL archiving / PITR** — a layer-2
  upgrade (Postgres `archive_command` + restart). **Tracked as a follow-up;** nightly
  is the immediate safety net and what this runbook covers today.

---

## 6. Escalation

| Symptom | Action |
|---------|--------|
| `/health/backup` 503 (stale / no successful backup) | check the nightly cron + `ops_backup_runs.error`; run `./akshara-backup.sh manual` |
| Latest restore drill `failed` | inspect `ops_restore_drills.mismatch`; treat the chain as unrestorable until a fresh drill passes |
| Artifact fails to decrypt | wrong/rotated key — verify `/opt/akshara/backup/secret.key`; do NOT proceed |
| `pg_restore` fails into throwaway db | do NOT `--force` production; open a platform ticket |

**Contacts:** Platform on-call via Control Center escalation.
