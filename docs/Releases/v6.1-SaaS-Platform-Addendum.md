## Executive Summary

This addendum closes SaaS platform gaps not fully specified in the v6.1 RBAC & Tenant Architecture document. It defines **two consoles** (Platform Control Center vs Organization Admin Console), **three CRM domains**, subscription lifecycle, seat counting, entitlements, renewal workflows, provisioning sagas, dedicated tenants, platform billing, white-label, export/offboarding, and long-term governance.

**No code, migrations, or Sprint 3 scope changes.**

## 1. Architecture Decisions (Addendum)

| ID | Decision | Rationale |
|----|----------|-----------|
| SA-01 | **Platform Control Center ≠ Organization Admin Console** | Different actors, routes, permissions, RLS scope |
| SA-02 | **Three CRM domains** with separate schemas and APIs | Platform sales, school admissions, customer success |
| SA-03 | **`organization_subscriptions.status` drives entitlements**; `organizations.status` mirrors for auth gate | Single enforcement source; org status synced |
| SA-04 | **Annual student slab** counts **billing-eligible active students** org-wide | Accurate multi-school aggregation |
| SA-05 | **Plans: Standard, Professional, Enterprise** + optional addons | Aligns with ACC-03 UI; extends slab model |
| SA-06 | **Renewal is a workflow**, not a cron line item | Quotes, reminders, approval, activation |
| SA-07 | **Provisioning is a saga** with compensation | Partial failure must not orphan tenants |
| SA-08 | **Platform billing tables are platform-scoped** (`tenant_id` = customer org) | Invoices owned by Akshara platform service |
| SA-09 | **Dedicated tier upgrade is async migration job** | No mobile/API contract change |
| SA-10 | **Break-glass access is audited, time-boxed, platform-only** | Support without RLS bypass for tenants |

## 2. Akshara Control Center Architecture

### 2.1 Two consoles (critical separation)

| Dimension | **Platform Control Center** | **Organization Admin Console** |
|-----------|----------------------------|-------------------------------|
| **Users** | Akshara internal staff | Customer org owner/admin |
| **JWT scope** | `platform` | `organization` |
| **Client routes** | `/control-center/*` (ACC-01..12) | `/org/*` or org section in admin shell (future) |
| **Data scope** | All organizations (aggregated) | Single `tenant_id` only |
| **RLS** | Platform policies + service role for cross-tenant reads | Org-scoped RLS + aggregate views |
| **Permissions** | `platform*` slugs | `viewOrganization`, `manageOrganization`, etc. |
| **API owner** | Platform Service (Edge Functions namespace `/platform/v1`) | Tenant Service (`/functions/v1/api`) |

**Deprecation fix:** Retire use of `manageControlCenter` for org admins. Split:

| Permission | Scope | Console |
|------------|-------|---------|
| `viewPlatformControlCenter` | platform | ACC read |
| `managePlatformControlCenter` | platform | ACC write |
| `viewOrganizationConsole` | organization | Org dashboard read |
| `manageOrganizationConsole` | organization | Org settings, schools, billing view |

Client `manageControlCenter` / `viewControlCenter` remain **platform-only** (superAdmin) until enum migration.

### 2.2 Platform teams & roles

| Team | Platform role slug | Primary ACC screens | Capabilities |
|------|-------------------|---------------------|--------------|
| **Super Admin** | `superAdmin` | All ACC-01..12 | Full platform; tenant lifecycle |
| **Platform Support** | `platformSupport` | ACC-06, ACC-10, schools registry | Tickets, monitoring; read-mostly |
| **Sales** | `platformSales` | ACC-05 CRM, ACC-02 schools (prospect) | Platform CRM pipeline |
| **Customer Success** | `platformCustomerSuccess` | ACC-07, ACC-03, ACC-09 | Health, renewals, usage |
| **Platform Finance** | `platformFinance` | ACC-04 billing, ACC-03 subscriptions | Invoices, credits, contracts |
| **Platform Operations** | `platformOps` | ACC-10 monitoring, ACC-12 settings | Incidents, feature flags, infra |

All platform roles: `scope=platform`, `tenant_id=null` in JWT, membership in `platform_staff_memberships` (Akshara internal org id constant).

### 2.3 Ownership boundaries

| Owned by Platform | Owned by Organization | Shared (read) |
|-------------------|----------------------|---------------|
| All tenants registry | Org profile, schools within org | Aggregated KPIs |
| Platform CRM deals | School operations | Subscription status (org view) |
| Invoices to customer | Internal school finance (fees) | Usage metrics |
| Support tickets (platform) | School admissions leads | Health score (CS view) |
| Feature flags rollout | School settings | |
| Dedicated infra provisioning | White-label brand assets (customer-uploaded) | |

### 2.4 Data visibility

| Data class | Platform Control Center | Org Admin Console |
|------------|------------------------|-------------------|
| Cross-tenant PII | **Denied** by default; aggregate only | N/A |
| Single-tenant PII | Via break-glass only (audited) | Full org scope |
| Billing / MRR | All tenants | Own org invoices & plan |
| Student counts | Aggregate per school/org | Per-school + org total |
| Admissions leads | **No access** (school CRM) | School scope after context switch |

### 2.5 Audit requirements

| Action | Audit event | Retention |
|--------|-------------|-----------|
| Platform user views tenant aggregate | `platformTenantViewed` | 7 years |
| Break-glass impersonation start/end | `platformImpersonationStarted/Ended` | 7 years |
| Subscription manual override | `subscriptionOverrideApplied` | 7 years |
| Tenant provisioned / suspended | `tenantProvisioned`, `tenantSuspended` | 7 years |
| Org admin creates school | `schoolProvisioned` | 7 years |

### 2.6 Future API ownership

| API prefix | Owner sprint | Methods (client) |
|------------|--------------|------------------|
| `/platform/v1/control-center/*` | Sprint 4+ | 12 Control Center repository methods |
| `/platform/v1/crm/*` | v7.6 Business Suite | Platform CRM |

## 3. CRM Architecture

### 3.1 Domain separation

```
┌─────────────────────────────────────────────────────────────────┐
│ PLATFORM CRM (Akshara sells to schools)                         │
│  platform_crm_leads → deals → provision_tenant                  │
│  Actor: platformSales | Scope: platform                         │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ SCHOOL ADMISSIONS CRM (school enrolls students)                   │
│  admissions_leads → applications → enrollment                   │
│  Actor: school staff | Scope: school | Module: Admissions        │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ CUSTOMER SUCCESS CRM (Akshara retains customers post-sale)      │
│  cs_accounts → health → renewals → support_link                 │
│  Actor: platformCustomerSuccess | Scope: platform + tenant ref  │
└─────────────────────────────────────────────────────────────────┘
```

**Rule:** No shared table between domains. Cross-links via `organization_id` foreign keys only.

### 3.2 Platform CRM

#### Lead lifecycle

```
new → contacted → qualified → demo_scheduled → demo_completed
  → proposal_sent → negotiation → won | lost | disqualified
```

| State | Entry trigger | Exit |
|-------|---------------|------|
| `new` | Web form, import, referral | SDR assigns |
| `qualified` | BANT criteria met | Demo booked |
| `demo_completed` | Demo notes filed | Proposal |
| `won` | Deal closed | **Provision Tenant saga** |
| `lost` | Reason code required | Archive |

#### Core entities (planned)

```
platform_crm_leads (id, company_name, contact_name, phone, email, source, status, owner_staff_id, ...)
platform_crm_activities (id, lead_id?, deal_id?, type, notes, scheduled_at, completed_at, staff_id)
platform_crm_deals (id, lead_id, organization_id?, stage, amount_paise, plan_slug, slab, expected_close, owner_staff_id)
platform_crm_quotations (id, deal_id, pdf_ref, valid_until, line_items JSONB, status)
platform_crm_demo_sessions (id, lead_id, scheduled_at, demo_type, notes, outcome)
```

#### Ownership model

- **Lead owner:** `platformSales` rep (`owner_staff_id`)
- **Deal owner:** may transfer; one primary owner
- **Handoff to CS:** on `won` → create `cs_accounts` row

#### Follow-up workflow

- Activities with `scheduled_at` → reminder jobs
- Stale lead: no activity 14 days → `platform_crm_tasks` escalation

### 3.3 School Admissions CRM

**Unchanged module ownership** — tables under Admissions domain:

```
admissions_leads, lead_notes, lead_followups, applications, ...
```

| Rule | Detail |
|------|--------|
| Scope | `tenant_id` + `school_id` |
| RLS | School staff only; org admin sees **aggregates** not raw leads |
| Marketing handoff | `Marketing.md` MK-02 → AD pipeline via `admissions_leads.source` |
| Platform CRM | **No FK** to `admissions_leads` |

### 3.4 Customer Success CRM

Post-sale; one `cs_accounts` row per `organization_id`.

```
cs_accounts (
  organization_id PK,
  success_owner_staff_id,
  health_score,          -- 0-100
  churn_risk,            -- low | medium | high
  onboarding_status,     -- not_started | in_progress | complete
  last_qbr_at,
  renewal_probability    -- 0.0-1.0
)

cs_playbooks (id, trigger, actions JSONB)
cs_health_signals (id, organization_id, signal_type, value, recorded_at)
```

| Workflow | Trigger |
|----------|---------|
| Onboarding | `provision_complete` event |
| Health refresh | Nightly job from usage + support + adoption |
| Renewal prep | 90 days before `current_period_end` |
| Churn intervention | `churn_risk=high` or health_score drop |

Support link: `support_tickets.organization_id` → CS account.

## 4. Subscription Lifecycle Architecture

### 4.1 State machine

```
                    ┌─────────┐
                    │  trial  │
                    └────┬────┘
           convert │    │ expire
                   ▼    ▼
              ┌─────────┐     payment fail / manual
              │ active  │──────────────────┐
              └────┬────┘                  │
     slab exceed │  │ period end          │
                 ▼  ▼ (no renew)          ▼
              ┌─────────┐            ┌───────────┐
              │  grace  │───────────►│ suspended │
              └────┬────┘            └─────┬─────┘
                   │ renew                   │ cancel / purge path
                   ▼                         ▼
              ┌─────────┐            ┌────────────┐
              │ active  │            │ cancelled  │
              └─────────┘            └────────────┘
```

### 4.2 States — definition & rules

| State | Definition | User visibility | ERP access |
|-------|------------|-----------------|------------|
| **trial** | Time-boxed evaluation; full or limited entitlements | “Trial — X days left” | Full per trial entitlements |
| **active** | Paid or approved contract in current period | Plan name + renewal date | Full per plan entitlements |
| **grace** | Slab exceeded OR renewal overdue within buffer | Warning banner | **Read + write** with warnings; block **new enrollments** |
| **suspended** | Grace expired OR manual suspend OR payment default | Login blocked or read-only | **Read-only** or **blocked** (configurable) |
| **cancelled** | Contract ended; retention window | Export offered | **No login** after optional wind-down |

### 4.3 Transitions & triggers

| From | To | Trigger | Actor |
|------|-----|---------|-------|
| trial | active | Trial conversion payment / manual approval | System / platformFinance |
| trial | suspended | Trial expiry without conversion | System job |
| active | grace | `student_count > slab_max + buffer` OR renewal overdue | System job |
| grace | active | Slab compliant OR renewal paid | System / payment event |
| grace | suspended | `grace_until` passed | System job |
| active | suspended | Manual (platform) OR severe ToS violation | platformOps / superAdmin |
| suspended | active | Reactivation payment + approval | platformFinance |
| * | cancelled | Owner request OR offboarding complete | organizationOwner / platform |
| cancelled | — | Retention elapsed → purge job | System |

### 4.4 Organization status synchronization

| `organization_subscriptions.status` | `organizations.status` | Auth: new JWT issue |
|------------------------------------|------------------------|---------------------|
| trial | trial | Allowed |
| active | active | Allowed |
| grace | active (with flag) | Allowed; `subscription_warning` claim |
| suspended | suspended | Denied or read-only token |
| cancelled | deleted (soft) | Denied |

Sync: trigger on subscription update → update `organizations.status` + bump `permissions_version`.

### 4.5 Trial rules

| Rule | Default |
|------|---------|
| Duration | 14 days (configurable per campaign) |
| Max students | 100 or plan slab minimum |
| Max schools | 1 |
| Modules | Standard entitlements subset |
| Conversion | Select plan + slab → `trial → active` |
| Extension | platformSales approval once, +7 days |

### 4.6 Grace rules

| Trigger | `grace_until` | Buffer |
|---------|---------------|--------|
| Slab exceeded | 30 days from exceed event | `grace_buffer_percent` on plan (default 10%) |
| Renewal overdue | 15 days past `current_period_end` | — |

During grace: emit `subscription_warning` in JWT; UI shows renewal CTA.

### 4.7 Suspension rules

- Block new student enrollments, new schools, API writes (except billing/export)
- Existing users: read-only or logout-only (enterprise: negotiate)
- platformSupport may unsuspend with audit

### 4.8 Reactivation rules

- Requires: outstanding invoice paid OR new contract + `organizationOwner` acceptance
- `suspended → active`: reset `grace_until`, extend `current_period_end` if renewal

### 4.9 Billing implications (no gateway in architecture)

| Event | Billing action |
|-------|----------------|
| trial → active | Generate first annual invoice (draft → issued) |
| renewal | Renewal invoice per quote |
| slab upgrade mid-year | Supplemental invoice (prorated annual — see §6) |
| suspension | Stop new charges; outstanding remains |
| cancellation | Final invoice if applicable; credit memo |

### 4.10 Audit

All transitions → `subscription_events (organization_id, from_status, to_status, reason, actor_id, metadata)`.

## 5. Student Seat Counting Rules

### 5.1 Student status definitions

| Status | Definition | Billable? |
|--------|------------|-----------|
| **active** | Enrolled, attending, current academic year | **Yes** |
| **inactive** | Temporarily not attending (medical, long leave); record kept | **No** |
| **withdrawn** | Left mid-year; off roll | **No** (from withdrawal date) |
| **alumni** | Graduated / completed; historical record | **No** |
| **transferred** | Moved to another school **in same org** | **No** at source; **Yes** at destination if active |

### 5.2 Counting rules

```
billing_eligible_count(org) =
  COUNT(DISTINCT student_id) WHERE
    status = 'active'
    AND tenant_id = org
    AND deleted_at IS NULL
```

| Rule | Detail |
|------|--------|
| Distinct student | One student in two schools (rare) counts **once** org-wide |
| Transfer | Same-day transfer: count at destination only |
| Inactive → active | Billable from reactivation date |
| Trial | Count toward trial cap, not annual invoice until active |

### 5.3 Reconciliation job

- **Frequency:** nightly + on-demand after enrollment/withdrawal
- **Output:** `organization_subscriptions.student_count_cached`, `student_count_computed_at`
- **Exceed slab:** if `count > slab_max * (1 + grace_buffer_percent/100)` → emit `slab_exceeded` → grace transition

### 5.4 Multi-school aggregation

```
Org "ABC Group"
  School A: 320 active
  School B: 280 active
  School C: 150 active
  ─────────────────
  Org total: 750 → slab "501-1000"
```

Per-school breakdown stored for org console; billing uses org total.

## 6. Subscription Plans & Entitlements

### 6.1 Plan tiers

| Plan | Target | Dedicated DB | Custom contract |
|------|--------|--------------|-----------------|
| **Standard** | Single school, <500 students | No | No |
| **Professional** | Multi-school chains | Optional add-on | Optional |
| **Enterprise** | Large groups, compliance | Eligible | Yes |

### 6.2 Schema (planned)

```
subscription_plans (
  slug PK,                    -- standard | professional | enterprise
  name, tier_rank INT,
  student_slab_min, student_slab_max,
  max_schools INT,
  grace_buffer_percent,
  billing_period CHECK (= 'annual'),
  base_price_paise,
  dedicated_db_eligible BOOLEAN,
  is_public BOOLEAN
)

plan_entitlements (
  plan_slug, entitlement_slug,  -- e.g. module.admissions, feature.ai_insights
  PRIMARY KEY (plan_slug, entitlement_slug)
)

subscription_addons (
  slug, name, entitlement_slug, price_paise_annual
)

organization_subscription_addons (
  organization_id, addon_slug, status
)
```

### 6.3 Entitlement model

| Type | Example slugs | Enforcement |
|------|---------------|-------------|
| Module | `module.admissions`, `module.transport` | Route guard + API middleware |
| Feature | `feature.api_access`, `feature.white_label` | Feature flag |
| Limit | `limit.schools`, `limit.students` | Subscription job |
| Tier | `tier.dedicated_db` | `deployment_tier` |

Resolved entitlements = plan entitlements ∪ addons ∪ `subscription_overrides` (enterprise JSONB).

### 6.4 Addon model

Examples: `addon.dedicated_db`, `addon.ai_pack`, `addon.extra_school_pack` (+5 schools).

### 6.5 Upgrade path

| Change | Behavior |
|--------|----------|
| Standard → Professional | New slab selection; supplemental invoice (prorated remaining months) |
| Slab 500 → 1000 | Immediate entitlement; grace if over new slab until paid |
| Add dedicated DB | Triggers **dedicated tenant migration saga** (§9) |

### 6.6 Downgrade path

| Change | Behavior |
|--------|----------|
| Enterprise → Professional | At **renewal only**; may require student/school count compliance |
| Slab downgrade | Effective next renewal; block if current count exceeds new slab |
| Remove dedicated DB | **Not automatic** — requires migration to shared; enterprise contract clause |

## 7. Renewal Workflow Architecture

### 7.1 Renewal lifecycle

```
upcoming → quote_generated → quote_sent → quote_accepted
  → invoice_issued → invoice_paid → renewed
                    ↘ quote_rejected → negotiation → ...
                    ↘ expired → grace → churn
```

### 7.2 Reminder schedule

| Days before `current_period_end` | Action | Owner |
|----------------------------------|--------|-------|
| 90 | CS review + health check | platformCustomerSuccess |
| 60 | Renewal quote draft generated | System |
| 60 | Email + in-app reminder to owner | System |
| 30 | Quote sent for approval | organizationOwner |
| 30 | Reminder if quote pending | System |
| 7 | Final reminder; escalate to CS | System |
| 0 | If unpaid → `active → grace` | System |
| -15 (grace end) | `grace → suspended` | System |

### 7.3 Core entities (planned)

```
renewals (
  id, organization_id,
  period_start, period_end,
  status,                   -- upcoming | quote_sent | accepted | invoiced | paid | expired
  plan_slug, slab_min, slab_max,
  quoted_amount_paise,
  owner_user_id,            -- org owner approver
  cs_owner_staff_id,
  created_at, updated_at
)

renewal_reminders (id, renewal_id, reminder_type, sent_at, channel)
```

### 7.4 Workflow jobs

| Job type | When |
|----------|------|
| `renewal_scan_upcoming` | Daily |
| `renewal_generate_quote` | T-60 |
| `renewal_send_reminder` | T-60, T-30, T-7 |
| `renewal_escalate_cs` | T-7 if quote not accepted |
| `renewal_activate` | On invoice_paid |
| `renewal_churn` | Grace expired |

### 7.5 Approvals

- Quote acceptance: `organizationOwner` (or delegated `manageSubscription` on org)
- Enterprise amendments: `platformFinance` co-sign on `subscription_overrides`

### 7.6 Churn handling

| Outcome | Action |
|---------|--------|
| Quote rejected | CS task; negotiation window 30 days |
| Grace expired | `suspended`; CS outreach |
| Cancel confirmed | Offboarding saga (§13) |
| Win-back | New deal in Platform CRM (separate from renewal record) |

## 8. Tenant Provisioning Saga

### 8.1 End-to-end flow

```
Lead Won (Platform CRM)
  → [1] create_organization
  → [2] create_organization_settings
  → [3] assign_subscription (trial or paid)
  → [4] create_billing_profile
  → [5] create_school (first)
  → [6] create_owner_user
  → [7] assign_organization_roles (owner)
  → [8] assign_school_roles (schoolAdmin)
  → [9] seed_roles_permissions
  → [10] seed_school_settings (academic year, currency)
  → [11] create_cs_account
  → [12] mark_ready + notify
```

### 8.2 Saga orchestration

```
provisioning_sagas (
  id, type,                    -- org_onboarding | school_add | dedicated_migration
  organization_id,
  idempotency_key UNIQUE,
  status,                      -- pending | running | completed | compensating | failed
  current_step, payload JSONB,
  created_at, updated_at
)

provisioning_saga_steps (
  id, saga_id, step_name, status, attempt, last_error, started_at, completed_at
)
```

Orchestrator: queue worker; each step **idempotent** via `idempotency_key` + step name.

### 8.3 Entry paths

| Path | Entry | Prefill |
|------|-------|---------|
| **Self-service** | Public wizard | User input |
| **Sales-assisted** | Platform CRM `deal.won` | Deal → org name, plan, owner phone |
| **Platform manual** | superAdmin “Create tenant” | Support form |

### 8.4 Retry strategy

| Failure type | Retry |
|--------------|-------|
| Transient DB | Exponential backoff, max 5 |
| Validation (slug taken) | Fail fast; no retry |
| External (email) | 3 retries |

### 8.5 Compensation / rollback

| Failed after step | Compensation |
|-------------------|--------------|
| 1–2 | Delete org if no schools/users |
| 5+ (school exists) | Mark org `provisioning_failed`; manual cleanup ticket |
| Never hard-delete paid org | platformOps alert |

**No automatic cascade delete** after user data exists.

### 8.6 Idempotency

- Client sends `Idempotency-Key` header on wizard submit
- Saga key = hash(phone + slug) or deal_id
- Re-submit returns existing saga status

### 8.7 Ready state

`organizations.provisioning_status = ready` → emit `tenant.provisioned` domain event → CS onboarding playbook starts.

## 10. Dedicated Tenant Architecture

### 10.1 Tiers (unchanged from v6.1)

| Tier | `deployment_tier` | Mobile/API |
|------|-------------------|------------|
| Shared | `shared` | Default Supabase project |
| Dedicated DB | `dedicated_db` | Same API URL; router selects DB pool |
| Dedicated infra | `dedicated_infra` | Optional dedicated API gateway host; same JWT |

**Mobile apps unchanged:** same OTP login; JWT `tenant_id` resolves backend.

### 10.2 Tenant routing

```
Request → API Gateway
  → decode JWT tenant_id
  → TenantResolver.load(organization_id)
  → connection_profile (host, pool, tier)
  → execute with RLS context
```

### 10.3 Provisioning flow (dedicated upgrade)

```
1. Enterprise contract + addon.dedicated_db
2. provisioning_saga type=dedicated_migration
3. Provision dedicated Supabase project / RDS
4. Run migrations
5. Snapshot copy from shared
6. Verify row counts
7. Update connection_profile
8. Cutover (maintenance window)
9. Retain shared data 90d (read-only archive)
```

### 10.4 Upgrade / downgrade

| Path | Supported |
|------|-----------|
| shared → dedicated_db | Yes (migration saga) |
| dedicated_db → dedicated_infra | Yes |
| dedicated → shared | **Enterprise exception only**; manual |

### 10.5 Operational model

| Concern | Shared | Dedicated |
|---------|--------|-----------|
| Backups | Platform schedule | Per-tenant schedule |
| Migrations | Single `db push` | Per-profile `db push` |
| Monitoring | Shared dashboards | Per-tenant + platform rollup |
| Cost | Included in slab | Pass-through + minimum commit |
