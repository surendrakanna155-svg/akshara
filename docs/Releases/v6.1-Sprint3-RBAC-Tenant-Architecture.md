# v6.1 — Sprint 3 Architecture: RBAC, Tenant Isolation & SaaS Platform

**Document ID:** `AKS-SPRINT3-ARCH-v1.0`  
**Status:** Architecture specification (no implementation)  
**Baseline:** v5.6 architecture · v6.0 core platform · v6.0 release closure  
**Sprint:** 3 (v6.1) — design only  
**Last updated:** June 2026

---

## Executive Summary

Sprint 3 evolves the v6.0 core platform from **authenticated but unscoped service-role access** into a **permission-driven, RLS-enforced multi-tenant SaaS**. This document defines organization hierarchy, RBAC catalog, multi-role employees, RLS strategy, org/group/parent/student access models, provisioning, subscription slabs, export/offboarding, and enterprise deployment tiers — without modifying v6.0 implementation.

**Sprint 3 gate (unchanged from roadmap):** Admissions + Finance + SIS APIs live on staging with server RBAC + RLS; 63 core module contract tests pass.

**Explicit non-goals (Sprint 3):** Communication Hub, Payment Engine, Marketing automation, AI inference services — architecture hooks only.

## 1. Architecture Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| AD-01 | **Organization = `tenant_id`** (unchanged) | Aligns with v5.6, v6.0 schema, Flutter `TenantContext` |
| AD-02 | **Permissions are data, not code** | Replace `permissions.ts` hardcoding with `permission_definitions` + resolver |
| AD-03 | **Roles are templates; memberships are assignments** | Supports multi-role employees without role explosion |
| AD-04 | **JWT carries resolved permission slugs + `permissions_version`** | Client cache invalidation; server remains authoritative |
| AD-05 | **RLS is authoritative for row access** | Middleware checks permission; PostgreSQL enforces tenant/school/relationship scope |
| AD-06 | **School groups via junction table** (canonical) | Schools may belong to multiple groups; no `schools.school_group_id` |
| AD-07 | **Org admin default scope = organization** | Cross-school read via aggregates; school write requires context switch |
| AD-08 | **Parent/student scopes are first-class JWT scopes** | RLS uses relationship tables, not school membership alone |
| AD-09 | **Annual student slab billing at organization level** | No per-month per-student metering |
| AD-10 | **Deployment tier is organization metadata** | `shared` \| `dedicated_db` \| `dedicated_infra`; mobile apps unchanged |
| AD-11 | **Provisioning is workflow-driven** | Wizard + idempotent jobs; no manual SQL for onboarding |
| AD-12 | **HS256 retained for Sprint 3; RS256 migration parallel track** | v6.0 interim; document cutover before production pilot |
| AD-13 | **Aggregated org reporting via materialized views / read replicas** | Raw PII tables remain school-scoped even for org admins |

## 2. Organization Hierarchy

### 2.1 Canonical model

```
Platform (Akshara)
└── Organization (tenant_id) ─────────────────────────────┐
    ├── organization_settings (branding, billing, flags) │
    ├── organization_subscriptions (slab, renewal)         │
    ├── school_groups (optional)                          │
    │     └── school_group_schools (junction)             │
    ├── schools ──────────────────────────────────────────┤
    │     ├── school_settings                             │  Org-wide
    │     └── operational data (admissions, SIS, …)     │  analytics
    └── users (global identity)                           │
          ├── organization_memberships                    │
          ├── school_memberships (+ multi-role)           │
          ├── school_group_memberships                    │
          ├── guardian_relationships (parent)             │
          └── student_profiles (student link)             │
```

### 2.2 Example: ABC Education Group

| Entity | Example |
|--------|---------|
| Organization | ABC Education Group (`tenant_id`) |
| Schools | School A, B, C (`school_id` each) |
| Future group | "South Region" → {School A, School B} |

### 2.3 Isolation vs reporting

| Layer | School A data | School B data | Org aggregate |
|-------|---------------|---------------|---------------|
| School staff JWT (`scope=school`) | Read/write per role | **Denied** | N/A |
| Org admin JWT (`scope=organization`) | Aggregated KPIs only | Aggregated KPIs only | ✅ |
| Group director JWT (`scope=school_group`) | If in group | If in group | Group KPIs |
| RLS | `school_id = app.school_id` | Blocked | `tenant_id` + aggregate views |

### 2.4 Cross-school analytics

- **Operational tables:** always `tenant_id` + `school_id`; never queried cross-school without aggregate layer.
- **Aggregate layer:** `org_kpi_snapshots`, `school_group_kpi_snapshots` — refreshed by jobs; org/group roles read these.
- **Organization settings:** `organization_settings` JSONB — branding, feature flags, module enablement per school.

### 3.2 Avoid role hardcoding

| Layer | Strategy |
|-------|----------|
| Database | `role_definitions`, `role_permissions`, `permission_definitions` |

| Client | Sync slugs from server; enum additions for UX only |
| Approvals | `approval_policies` reference **permissions**, not roles |

## 4. Multi-Role Employee Model

### 4.1 Problem

v6.0 `school_memberships` has **one role per (user, school)**. Real schools assign multiple hats (Teacher + Coordinator).

### 4.2 Database structure (proposed)

**Option chosen: membership + role assignments (many-to-many)**

```
school_memberships (
  id, user_id, school_id, status, permissions_version, ...
  -- role column DEPRECATED → migrated to assignments
)

school_membership_roles (
  id,
  school_membership_id UUID FK,
  role_slug TEXT FK → role_definitions.slug,
  is_primary BOOLEAN DEFAULT false,
  effective_from DATE,
  effective_to DATE,
  status TEXT,  -- active | suspended
  UNIQUE (school_membership_id, role_slug)
)
```

Organization memberships follow the same pattern via `organization_membership_roles`.

### 4.3 Permission resolution strategy

```
effective_permissions(user, active_context) =
  UNION(
    permissions_for_role(r) for r in active_role_assignments,
    membership_permission_grants,
    DENY overrides
  )
```

| Rule | Behavior |
|------|----------|
| Union | User gets **union** of all active role permissions |
| DENY wins | `membership_permission_overrides` with `effect=deny` removes slug |
| Primary role | `is_primary` drives UI label and default dashboard |
| Conflicts | Same module `manage*` from two roles → still `manage*` (no downgrade) |
| Approval | Approver needs permission slug; any qualifying role suffices |

### 4.4 JWT at issue time

Embed **resolved flat permission list** + `primary_role` + `role_slugs[]` for audit display.

### 4.5 Audit implications

| Event | Payload |
|-------|---------|
| `roleAssigned` | `membership_id`, `role_slug`, `actor_id` |
| `roleRevoked` | same |
| `permissionOverride` | `slug`, `effect`, `reason` |
| API access | Log `active_role_slugs`, `permission_used` |

## 5. Permission Architecture

### 5.1 Naming strategy

```
{verb}{Module}[{Resource}]

verb: view | manage | approve | export | administer
module: PascalCase domain — Admissions, Finance, Sis, Hr, Inventory, ...
```

**Stable slugs (snake/camel as today):** `viewAdmissions`, `manageFinance`, `approveRefunds`.

**Future modules:**

| Module | View | Manage | Approve | Administer |
|--------|------|--------|---------|------------|
| Communications | `viewCommunications` | `manageCommunications` | — | `sendBroadcast` |
| Marketing | `viewMarketing` | `manageMarketing` | `approveCampaigns` | — |
| Payments | `viewPayments` | `managePayments` | `approvePayments` | — |
| AI | `viewAiInsights` | `manageAiPolicies` | — | `runAiCopilot` |

### 5.2 Permission catalog tables

```
permission_definitions (
  slug TEXT PK,
  module TEXT,
  action TEXT,
  scope TEXT,  -- organization | school | group | self | platform
  description TEXT,
  is_system BOOLEAN DEFAULT true
)

permission_groups (
  id, slug, name, module  -- UI bundles: "Finance Operations"
)

permission_group_members (
  group_id, permission_slug
)
```

### 5.3 Inheritance

| Level | Inherits from |
|-------|---------------|
| `role_permissions` | Default grants per role slug |
| `organization_membership_roles` | Org-scoped roles only org permissions |
| `school_membership_roles` | School-scoped roles |
| `membership_permission_overrides` | Explicit grant/deny per membership |

**No implicit inheritance across scopes** — org admin does not inherit school `manage*` without assignment.

### 5.4 Ownership strategy

| Permission scope | Data owner table | RLS driver |
|------------------|------------------|------------|
| `organization` | `organizations` | `tenant_id` |
| `school` | `schools` | `tenant_id` + `school_id` |
| `school_group` | `school_groups` | `tenant_id` + group junction |
| `self` | `users`, guardians, students | relationship FK |
| `platform` | Akshara internal | service role only |

## 6. Row Level Security (RLS)

### 6.1 Goals

- School A **never** reads School B rows.
- Parent sees **only linked children**.
- Student sees **only own record**.
- Org admin sees **aggregates** for cross-school; raw PII only with explicit grant + audit.

### 6.2 JWT claim requirements (v6.1 target)

| Claim | Type | Required when |
|-------|------|---------------|
| `sub` | UUID | Always |
| `tenant_id` | UUID | Always |
| `organization_id` | UUID | Always (= tenant_id) |
| `scope` | enum | Always — see below |
| `school_id` | UUID? | `scope=school` |
| `school_group_id` | UUID? | `scope=school_group` |
| `student_id` | UUID? | `scope=student` |
| `child_ids` | UUID[]? | `scope=parent` |
| `role_slugs` | string[] | Staff scopes |
| `primary_role` | string | UX / audit |
| `permissions` | string[] | Resolved effective set |
| `permissions_version` | int | Cache bust |
| `session_id` | UUID | Session revoke |
| `deployment_tier` | string | Routing (optional in JWT; can resolve from org) |

**Scope enum:** `school` | `organization` | `school_group` | `parent` | `student` | `platform`

### 6.3 Session variables (set per request before queries)

```sql
SELECT set_config('app.tenant_id',     '<uuid>', true);
SELECT set_config('app.scope',         '<scope>', true);
SELECT set_config('app.school_id',     '<uuid|null>', true);
SELECT set_config('app.school_group_id','<uuid|null>', true);
SELECT set_config('app.user_id',       '<uuid>', true);
SELECT set_config('app.student_id',    '<uuid|null>', true);
SELECT set_config('app.parent_user_id','<uuid|null>', true);
```

Helper: `auth.set_request_context(jwt_claims)` PL/pgSQL called from Edge middleware via RPC.

### 6.4 Policy strategy

**Pattern A — Standard school operational table**

```sql
ALTER TABLE admissions_leads ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON admissions_leads
  USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND (
      current_setting('app.scope', true) = 'organization'
      AND current_setting('app.school_id', true) IS NULL
      -- org scope: deny raw row access; use aggregate views instead
      AND false
    OR (
      current_setting('app.scope', true) = 'school'
      AND school_id = NULLIF(current_setting('app.school_id', true), '')::uuid
    )
    OR (
      current_setting('app.scope', true) = 'school_group'
      AND school_id IN (
        SELECT school_id FROM school_group_schools
        WHERE school_group_id = NULLIF(current_setting('app.school_group_id', true), '')::uuid
      )
    )
  )
);
```

**Pattern B — Parent access (student-linked)**

```sql
-- student_guardians links parent user to student
CREATE POLICY parent_student_access ON student_attendance
  USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND current_setting('app.scope', true) = 'parent'
    AND student_id IN (
      SELECT student_id FROM student_guardians
      WHERE guardian_user_id = current_setting('app.parent_user_id')::uuid
        AND status = 'active'
    )
  );
```

**Pattern C — Student self access**

```sql
CREATE POLICY student_self_access ON student_assignments
  USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND current_setting('app.scope', true) = 'student'
    AND student_id = current_setting('app.student_id')::uuid
  );
```

**Pattern D — Org aggregate views**

```sql
CREATE VIEW org_admissions_kpis WITH (security_invoker = true) AS
  SELECT tenant_id, school_id, count(*) FILTER (...) ...
  FROM admissions_leads GROUP BY 1, 2;

-- RLS on view: org scope allowed; school scope filtered to app.school_id
```

### 6.5 Supabase RLS approach

| Concern | Approach |
|---------|----------|
| Edge Functions today use service role | Middleware **must** call `set_request_context` then use **user-scoped** connection or `supabase.rpc` with SECURITY DEFINER wrapper |
| Sprint 3 target | Introduce `db_user` role with RLS; service role only for provisioning/cron |
| PostgREST (future) | JWT from Supabase Auth **or** custom JWT via `auth.jwt()` hook — RS256 track |
| Testing | Tenant isolation test suite per scope (extends v4.3 client tests) |

### 6.6 Employee isolation

Employees are school-scoped via `school_membership_roles`. HR tables include `employee_id` linked to `user_id`; RLS ensures `school_id` match. Cross-school employee transfer = workflow event, not shared row.

## 7. Organization Admin Access Model

| Dimension | Access |
|-----------|--------|
| **Visibility** | All schools in org — lists, KPIs, seat usage, subscription status |
| **Edit** | Org profile, branding, billing, school provisioning, group CRUD, feature flags |
| **School ops write** | **Denied** unless context-switched to school + school role with `manage*` |
| **Reporting** | Org dashboards, cross-school analytics, export at org level (with `exportOrganization` permission) |
| **Audit** | All org-admin mutations; cross-school report access logged |

**Owner vs Admin:** `organizationOwner` includes billing/legal actions (`administerBilling`, `manageSubscription`); `organizationAdmin` may be delegated without billing.

## 9. Parent & Student Isolation

### 9.1 Relationship model

```
students (
  id, tenant_id, school_id, user_id?, ...  -- user_id set when student has login
)

student_guardians (
  id, tenant_id, school_id,
  student_id, guardian_user_id,
  relationship TEXT,  -- mother | father | guardian
  is_primary BOOLEAN,
  status TEXT
)

parent_school_memberships (
  -- optional: links parent to school for scope discovery at login
  user_id, school_id, status
)
```

### 9.2 Login / scope resolution

| User type | Resolution |
|-----------|------------|
| Parent | OTP → find guardian links → if multiple schools, school picker → `scope=parent`, `child_ids[]`, `school_id` |
| Student | OTP → find `students.user_id` → `scope=student`, `student_id`, `school_id` |

### 9.3 Access model

| Actor | Can access |
|-------|------------|
| Parent | Own children's attendance, fees, homework, messages — per school |
| Student | Own academic record, timetable, assignments — read-only APIs default |

### 9.4 Audit

Log `child_id` / `student_id` accessed on every parent/student API call.

### 10.1 Deployment tiers

|------|-------------------|-----|-------|
| Standard | `shared` | Shared Supabase project, RLS isolation | Shared Edge Functions |
| Enterprise DB | `dedicated_db` | Dedicated Postgres (Supabase dedicated or RDS) | Shared compute |

### 10.2 Tenant resolver (no mobile app changes)

```
organizations.deployment_tier
organizations.connection_profile_id  → tenant_connection_profiles (host, pooler, secrets ref)
```

Mobile/web continues: `API_BASE_URL` + JWT. Resolver at API gateway:

1. Decode JWT `tenant_id`
2. Load `connection_profile` from cache
3. Route DB pool / Supabase project

### 10.3 Database routing

| Component | Strategy |
|-----------|----------|
| Connection pool | PgBouncer per profile; Edge Function selects pool by `tenant_id` |
| Migrations | Same migration set applied to all tiers; `supabase db push` per dedicated project |

```
  id, organization_id, from_tier, to_tier,

)
```

Workflow: snapshot → provision dedicated → replay migrations → copy data → DNS cutover → verify → decommission old rows in shared (after retention).

## 12. Subscription Architecture

### 12.1 Annual student slab model

```
subscription_plans (
  slug, name,
  student_slab_min INT, student_slab_max INT,  -- e.g. 0-500, 501-1000
  billing_period TEXT CHECK (billing_period = 'annual'),
  base_price_paise INT,
  grace_buffer_percent INT DEFAULT 10
)

organization_subscriptions (
  organization_id, plan_slug,
  status,  -- trial | active | grace | suspended | cancelled
  current_period_start, current_period_end,
  student_count_cached INT,
  grace_until TIMESTAMPTZ
)
```

### 12.2 Multi-school aggregation

- **Seat count** = sum of active `students` across all schools in org (dedupe transfers)
- **Enforcement:** soft block at slab + grace; hard block at suspension
- **Renewals:** annual invoice; renewal job 30/7/1 days before expiry
- **Discounts / enterprise:** `subscription_overrides` JSONB on org

**No monthly per-student billing.**

### 12.3 Billing profile

```
billing_profiles (
  organization_id, legal_name, gstin, billing_email,
  payment_method_ref, address JSONB
)
```

Payment provider integration deferred to Payment Engine (v7.0); Sprint 3 stores profile + slab enforcement hooks.

## 20. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| RLS + service role bypass | Critical | Mandatory `set_request_context`; integration tests |
| Multi-role permission explosion | High | Union with DENY overrides; cap audit verbosity |
| Org admin PII exposure via aggregates | High | Separate views; no raw table access for org scope |
| HS256 JWT | Medium | RS256 parallel track |
| Dedicated tenant routing complexity | Medium | Defer `dedicated_*` to Sprint 5+; design now |
| Client enum drift | Medium | `ClientBackendAlignment.md` sync in Sprint 3 |
| Subscription enforcement without payment provider | Low | Soft limits + manual billing until v7.0 |
| School group scope in Sprint 3 vs 4 | Medium | Schema in Sprint 3; APIs Sprint 4 |

## 22. Future Scalability Considerations
