## 1. Executive Summary

Admissions is the **reference implementation** for ERP API integration. All **11** `AdmissionsRepository` methods are wired through Dio → DTO → mapper → repository → provider → screen. Happy-path coverage is strong; production gaps center on **error normalization**, **DTO type safety**, and **pagination**.

## 3. DTO Coverage — **8 / 10**

### Strengths

- Shared envelope: `api_envelope_dto.dart`, `api_error_dto.dart`, `pagination_dto.dart`
- List responses use `{ data: { items: [...] } }` consistently
- `AdmissionsEnumCodec` handles snake_case and camelCase API strings
- One DTO file per aggregate (11 domain DTOs + shared infra)

### Gaps

| ID | Gap | Impact |
|----|-----|--------|
| ADM-D01 | Item DTOs are raw `Map<String, dynamic>` wrappers | No compile-time backend contract |
| ADM-D02 | `PaginationDto` parsed but never passed to domain/repository | Large lists won't scale |
| ADM-D03 | `ApiErrorDto` throws `StateError` in DTO layer, not `ApiFailure` | Logical 200+error responses break UX pipeline |
| ADM-D04 | `RepositoryQuery` is tenant-only — no filters, sort, or cursor | Lead/report filters are client-side only |
| ADM-D05 | Tenant sent as both headers (interceptor) and query params | Backend must reconcile dual propagation |

## 4. Mapper Quality — **8.5 / 10**

**File:** `lib/core/repositories/api/admissions/mapper/admissions_mapper.dart`

### Strengths

- Dedicated `to*` method per aggregate; nested structures (pipeline, reports, settings, prefill) fully mapped
- Defensive null coalescing and enum codec for all admissions enums
- Contract tests validate mapping against mock repository output

### Gaps

- Silent defaults (`''`, `0`, enum fallbacks) can mask API drift
- KPI icons derived client-side from `id` — not from API payload
- Flutter `Material` import in core mapper (`IconData`) — layering coupling
- Contract assertions are shallow (counts + one field, not deep equality)

---

## 5. Error Handling — **6.5 / 10**

### Stack

```
Dio → ApiErrorInterceptor → ApiFailureMapper → AsyncValue.error
     → resolveAdmissionsAsync → AdmissionsAsyncBody → AksharaErrorState.fromFailure
```

### Strengths

- HTTP errors (401, 403, 404, 5xx, timeout, network) mapped to typed `ApiFailure`
- `isRetryable` respected — 401/403 hide retry button
- Correlation ID captured from request headers

### Gaps

| ID | Gap | Severity |
|----|-----|----------|
| ADM-E01 | Envelope `{ error: ... }` on 200 → `StateError` → generic unknown failure | P1 |
| ADM-E02 | 4xx response body not parsed via `ApiErrorDto` in interceptor | P1 |
| ADM-E03 | Null response body → `{}` → empty domain defaults (silent failure) | P1 |
| ADM-E04 | Contract/integration tests use fake Dio **without** `ApiErrorInterceptor` | P2 |
| ADM-E05 | No admissions-specific error-path tests | P2 |

## 6. Retry Strategy — **7.5 / 10**

**Pattern:** `retryAdmissionsFuture(ref, futureProvider)` → `ref.invalidate(provider)`

### Wired screens (10/11 flows)

Dashboard, Leads, Lead detail, Applications, Documents, Approval, Reports, Settings, Enrollment, Fee handoff.

### Gaps

- `admissionsPendingEnrollmentsViewStateProvider` exists but no screen uses `AdmissionsAsyncBody` + retry (consumed by SIS tests only)
- Fee handoff retries handoffs provider only — fee structures fetch has no independent retry UI
- Full reload on retry (no stale-while-revalidate)

---

## 7. Provider Async Patterns — **8 / 10**

**Files:** `lib/features/admissions/admissions_async_state.dart`, 11 `*_provider.dart` files

### Pattern

```
FutureProvider<T> → *ViewStateProvider (resolveAdmissionsAsync) → AdmissionsAsyncBody
```

Legacy `*LoadingProvider` / `*ErrorProvider` / `*EmptyProvider` retained for widget test overrides via `watchRepositoryFuture`.

### Strengths

- Consistent across all admissions screens post-v1.9
- Manual test overrides still work (force loading/error/empty)
- `ApiFailure`-aware error messages and retry

### Gaps

- Dual state systems (legacy triads + ViewState) increase provider count (~9 state providers per screen cluster)
- Lead detail uses family provider without dedicated ViewState in some paths

---

## 8. Repository Implementation — **9 / 10**

**File:** `lib/core/repositories/api/admissions/api_admissions_repository.dart`

Thin pass-through: `remote.fetch* → mapper.to*`. No `ApiNotConnectedException` stubs.

### Strengths

- Complete interface implementation
- Injectable mapper for testing
- Feature-flagged via `admissionsRepositoryProvider`

### Gaps

- Read-only (GET only) — no mutations
- No pagination or filter passthrough at repository level

---

## 11. Verdict

Admissions API is **structurally production-ready for read-only GET flows** when the backend matches the envelope contract. The module serves as a **proven template** for Finance (v2.1) and future module rollouts. Primary risks before live deployment are error normalization and pagination — not missing endpoints or mappers.
