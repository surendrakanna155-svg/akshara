## 4. Domain Review

### 4.1 Architecture ✅ Strong

**Strengths**
- Consistent DTO → Mapper → Remote → ApiRepository pattern across all 14 API-enabled domains
- Per-module feature flags enable gradual rollout without code changes
- Shared network layer (Dio, interceptors, ApiFailure) eliminates raw exception leakage to UI
- Riverpod `FutureProvider` + `watchRepositoryFuture` pattern standardized post v3.0
- OpenAPI contract registry enables staging validation gates (v2.8)

**Weaknesses**
- 11 duplicate `*ModuleScaffold` widgets (~2,200 LOC) — maintenance burden (TD-P2-01)
- ~1,600 providers with broad rebuild fan-out (TD-P1-08)
- Mobile apps still default to mock repos; API flags off until backend deploys

**Assessment:** Architecture is **production-grade on the client**. No duplicate patterns introduced in v2.0–v4.2 trajectory.

### 4.2 API Coverage ✅ Client Complete / ⚠️ Backend Partial

**Release arc (v2.0–v4.2)**

| Release | Contribution |
|---------|-------------|
| v2.0 | Auth foundation, JWT, audit local store |
| v2.1–v2.4 | Finance read APIs |
| v2.2 | Auth server integration, permission sync |
| v2.3 | SIS read API |
| v2.5–v2.6 | Admissions + Finance + SIS write APIs |
| v2.8 | OpenAPI validation, audit upload client |
| v2.9 | HR + Transport read (19 methods) |
| v3.2 | Remaining 6 ERP modules read (54 methods) |
| v4.2 | Mobile read APIs (29 methods) |

**Gaps**
- 8 ERP repository methods without live API client (6% of ERP)
- 6 modules have **zero write APIs** — mutations remain mock-only when flags enabled
- OpenAPI spec covers subset of live endpoints; v3.2 module paths partially documented
- Staging contract tests require `STAGING_CONTRACT_TESTS=true` + live backend

**Assessment:** **Client API layer ready for staging.** Backend must deploy and pass contract tests before production flags.

### 4.3 Security ⚠️ Client Strong / Server Critical Gap

**Client (v2.7 + v4.0)**
- Secure token storage (native encrypted)
- JWT claim validation, refresh rotation, reuse detection
- Session expiration policy, revocation service
- 401 → forced logout (v4.0)
- Production env: `requireTls`, `requireAuthentication`, `disableDemoAuth`

**Gaps**
- TD-P0-01: No server-side RBAC / tenant RLS — **authorization bypass via direct API**
- TD-P2-12: `allowAnonymous: true` on Dio in non-production environments
- TD-P1-07: Demo OTP / mock JWT paths remain for mobile personas
- No penetration test (checklist S6)
- TLS enforcement flag exists but not validated end-to-end (S5)

**Assessment:** Client security posture is **88/100** (v2.7 baseline). **Production security requires server enforcement** — client guards are UX-only.

### 4.4 RBAC ⚠️ View Complete / Mutations Partial

**Implemented**
- 22 permissions (view / manage / approve)
- `ErpRouteGuard` on all 12 ERP route prefixes
- `ManagePermissionGuard`, `ApprovePermissionGuard` with denied-access audit
- Server permission sync on login/refresh (when Auth API enabled)
- Permission cache version tracking

**Gaps**
- TD-P0-01: Server RBAC not enforced
- TD-P1-04: `AksharaManageAction` scaffold exists; **not wired on mutation screens**
- R9 checklist item unchecked for all environments beyond demo

**Assessment:** Route-level **view** RBAC is production-ready. **Mutation** RBAC is incomplete on UI and absent on server.

### 4.5 Tenant Isolation ⚠️ Partial

**Implemented**
- `TenantContext` + `TenantInterceptor` on all authenticated requests
- `RepositoryQuery` propagates tenantId / schoolId / organizationId
- `TenantMockScope` filters 4 core mocks (Admissions, Finance, SIS, HR) — v4.0
- Control Center mock has multi-tenant seed data

**Gaps**
- TD-P2-02: 10 mock repositories still return full demo data regardless of tenant
- TD-P0-01: No server-side row-level security
- Cross-tenant leakage possible via API if backend lacks RLS

**Assessment:** Client tenant **headers** are ready. Client mock **isolation** is partial. Server **RLS is mandatory** for SaaS.

## 12. Conclusions

1. **Client engineering is production-grade.** Architecture, test coverage, and API client wiring represent a mature Flutter ERP platform ready for backend integration.

2. **Production SaaS is blocked by server dependencies.** TD-P0-01 and TD-P0-02 are non-negotiable before any production tenant data.

3. **The 99/100 headline score measures client maturity, not deployability.** This review scores **72/100** for production SaaS deployment using deployment-weighted criteria.

4. **Demo and pilot (mock) deployments are safe today.** Staging with live backend is achievable for Admissions/Finance/SIS once backend deploys and contract tests pass.

5. **Next critical path is v4.3** — server RBAC/RLS validation — not additional client features.

6. **Governance and documentation are assets.** The release/audit/debt/checklist loop enables autonomous multi-milestone execution with clear stop conditions.
