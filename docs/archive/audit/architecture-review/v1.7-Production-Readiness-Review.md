## 1. Executive Summary

Akshara ERP has completed a **production-shaped client architecture** in v1.6: async tenant-aware repositories, centralized RBAC, route guards, and permission-driven navigation. The system remains a **high-fidelity mock MVP** on the data plane — all 102 repository methods resolve to in-memory mocks by default, and all API implementations throw `ApiNotConnectedException`.

**Verdict**

| Environment | Status |
|-------------|--------|
| Demo / staging (mock data) | **READY** |
| Staging with API flag enabled | **NOT READY** (immediate UI failure) |
| Production multi-tenant SaaS | **NOT READY** |

**Production Readiness Score: 58 / 100** (↑ from ~42/100 at v1.5)

The largest delta since v1.5 is **client security architecture** (RBAC + route guards + tenant propagation). The largest remaining gap is **backend integration** (0% live API, ~10% DTO coverage, no server enforcement).

## 11. Performance

### 11.1 Provider explosion — **MEDIUM RISK**

| Pattern | Approx. count |
|---------|---------------|
| `FutureProvider` | ~270 |
| Loading/error/empty `StateProvider` triads | ~200+ |
| Bridge `Provider` (`watchRepositoryFuture`) | ~100+ |

Each screen navigation may trigger multiple parallel `FutureProvider` resolutions. No `keepAlive` / caching strategy beyond Riverpod defaults.

### 11.2 Rebuild risks — **MEDIUM**

- `repositoryQueryProvider` watched by many futures — tenant change invalidates broad subtree
- `adminNavDestinationsProvider` rebuilds rail on any RBAC change (acceptable)
- Integration providers chain 3–4 watches (handoff queues)

### 11.3 Large list rendering — **HIGH RISK (production data)**

~65+ screens render full lists/tables via `ListView` / custom tables without:
- Pagination
- Virtualization (`ListView.builder` with lazy loading)
- `AksharaResponsiveTable` abstraction

Mock data (4–10 rows) masks performance debt.

**Performance audit score: 6.5 / 10**
